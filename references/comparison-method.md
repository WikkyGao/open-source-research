# 功能与业务流程对照方法论

目标产出不是"项目推荐列表"，而是**能直接指导自家 PRD 修订和开发决策的对照结论**。

## 一、步骤 1：从 PRD 抽取检索输入

读完 PRD 后，产出三样东西，再开始检索：

1. **领域关键词（中英各一组）**
   中文用于 Gitee / CNB 检索，英文用于 GitHub 检索。
   例：PRD 讲的是"教培机构课消管理" →
   中文：`课消 培训机构 排课 课时`、`教务管理系统`；
   英文：`course consumption`、`tutoring management`、`student class scheduling`。

2. **核心实体清单**（名词）
   例：学员、课程、课时包、排期记录、教师、教室、订单、凭证。
   → 用于后续验证候选项目的数据模型是否覆盖。

3. **核心业务流程清单**（动词 + 流程名）
   例：购课→开户→排课→上课→课消确认→课时扣减→月度结算。
   → 后续业务流程对照的主轴。

**判据**：如果抽不出 ≥3 条流程，说明 PRD 太粗，先回 PRD 侧补充，不要硬检索。

## 二、步骤 2：候选筛选打分

对每条候选打三项分（各 1~5 分），总分 ≥10 才进入深度分析：

| 维度 | 5 分 | 3 分 | 1 分 |
|---|---|---|---|
| 领域相关度 | 完全同一业务领域 | 相邻领域，有可复用模块 | 只是技术栈相同 |
| 活跃度 | 近 3 个月有提交 | 近 1 年有提交 | 超过 2 年无提交 |
| 完整度 | 含后端 + 数据模型 + 部署文档 | 只有前端或只有 demo | 只有 README |

剔除项（硬否决，不打分）：
- License 为 AGPL 且计划商用闭源（除非只做思路参考）
- 纯教程 / 课程作业 / 课程设计
- 仓库主体是文档、书籍、资源列表

## 三、步骤 3：功能对照矩阵

行 = 自家 PRD 的功能点，列 = 候选项目，单元格用以下符号，**不要写长句**：

| 符号 | 含义 |
|---|---|
| ✅ | 原生支持，实现完整 |
| 🟡 | 部分支持 / 实现较粗糙，需改造 |
| ⚪ | 有相关概念但实现路径不同（需写清差异） |
| ❌ | 未发现支持 |
| ➖ | 该项目不涉及此领域，不适用 |

矩阵后面必须跟一段**差异说明**，只讲 ➖ 以外符号里最有价值的 3~5 个格子：
"为什么它有而我们没有"、"它的实现方式与我们的设想差在哪"。

## 四、步骤 4：业务流程对照（本技能的核心产物）

对每个核心流程，按四要素对照：

```
流程名：课消确认
  触发条件：自家 PRD → 教师点击确认 / 系统定时
            候选项目 → 教师端手动 + 学员扫码双通道
  参与角色：自家 PRD → 教师、教务
            候选项目 → 教师、学员、系统（多一个学员确认环节）
  状态流转：自家 PRD → 待确认 → 已确认 → 已扣课时
            候选项目 → 待确认 → 已确认 → 已结算 → 已开票（多两级）
  异常分支：自家 PRD → 未定义
            候选项目 → 请假顺延、课时不足告警、跨月冲销
```

产出时遵循三条硬性要求：
1. **异常分支必须单独列出**。开源项目真正的价值往往在异常分支——自家 PRD 通常只画了happy path。
2. **状态机差异要画成对比，不能只写文字描述**。
3. **发现自家 PRD 缺失的环节，直接单列一节"建议补充到 PRD"**，给出具体补充条款文本。

## 五、步骤 5：差距分析三级分类

| 级别 | 定义 | 处理方式 |
|---|---|---|
| A 可直接借鉴 | 实现细节、交互模式、字段设计 | 抄思路，写进开发指引 |
| B 需改造复用 | 领域相近但业务规则不同 | 写清改造点与风险 |
| C 完全缺失 | 开源界也没做好 | 标为自研难点，写进 SOP 风险项 |

## 六、步骤 6：License 与合规提示

必须在报告里单列一节，逐项目写明：
- License 类型
- 是否允许闭源商用（MIT/Apache-2.0/BSD 允许；GPL 传染；AGPL 网络服务也传染）
- 结论：**只参考设计** 还是 **可以直接抄代码**

不写 License 判定的对标报告是废报告——这会直接导致后续开发踩法律坑。

## 七、输出纪律

- 每条结论必须能追溯到具体仓库的具体文件/章节，禁止写"某项目采用了类似方案"这种无源断言。
- 引用格式：`仓库名 → 文件路径或章节名`。
- 不确定就标"待确认"，不要编。
